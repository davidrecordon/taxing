# Claude Code Guidelines

This is a Federal & multi-state estimated tax calculator built with Next.js, TypeScript, and Tailwind CSS. The web app is client-only: the figures a person types never leave the browser. The one piece of server code is the MCP endpoint at `app/api/mcp/route.ts`, which runs the same calculations for AI assistants and other programs on the inputs in each request and stores nothing.

The repository is public. Never put real personal or financial details in code, tests, docs, or commit messages; build test cases from round, synthetic figures or from official worked examples.

## Project Structure

```
app/                    # Next.js App Router
  api/mcp/             # MCP endpoint (see "MCP Interface" below)
components/
  Forms/               # Input form components
  Displays/            # Result display components
  Modals/              # Modal dialogs
  UI/                  # Reusable UI components
  States/              # State-specific breakdown components
  shared/              # Shared display components
  TaxCalculator.tsx    # Main orchestrator component
data/                  # Tax brackets, deductions, limits (JSON), VERIFICATION.md
design_docs/           # Design documents, kept locally and ignored by git (see below)
lib/                   # Calculation logic (see lib/README.md)
  mcp/                 # MCP server: tool schemas, result summaries, server
  states/              # One calculator per state, plus stateCalcUtils.ts
  __tests__/           # Calculation tests and shared test data
```

`README.md` files in `components/`, `data/`, `lib/` and `lib/__tests__/` describe each area. Refer to them regularly, and update them in the same change whenever they would otherwise go stale. `AGENTS.md` is generated by `next dev` and points to the Next.js docs bundled in `node_modules`.

## Commands

```bash

bun run build       # Production build
```

## Key Patterns

### State Support Pattern

Each supported state follows the same structure:

1. **Data files**: `data/{state}-brackets.json`, `data/{state}-limits.json`, and `data/{state}-deductions.json` where the state has its own deductions or exemptions
2. **Types**: `{State}LimitsData` interface, plus the `TaxState` union and `STATE_LABELS`, in `lib/types.ts`
3. **Data loading**: a loader in `lib/stateData.ts` (state data is loaded on demand)
4. **Calculator**: `lib/states/{state}TaxCalculator.ts`
5. **Component**: `components/States/{State}Breakdown.tsx`
6. **Tests**: `lib/__tests__/{state}TaxCalculator.test.ts`, with data exported from `lib/__tests__/testData.ts`
7. **Integration**: Wire up in `TaxCalculator.tsx`, `TaxResultsDisplay.tsx`, `ConfigurationSection.tsx`

### Calculation Flow

```
TaxInputs → lib/calculate.ts → federalTaxCalculator → stateCalculator → CalculationResults → Display components
```

`lib/calculate.ts` is the one place that runs the federal and state calculators together: `TaxCalculator.tsx`, the test helper `lib/__tests__/calculateResults.ts` and the MCP server all call it. The federal calculation runs first. Some states depend on it: Colorado starts from federal taxable income, and DC must take the same type of deduction (standard or itemized) as the federal return, so for DC both types are calculated and the pair with the lower combined tax is used (`lib/deductionChoice.ts`). Colorado goes through the same choice, because its charitable subtraction is only for filers who take the federal standard deduction. State calculators that tax all income as ordinary income get wages, gross income, loss offsets and AGI from `calculateStateIncome()` in `lib/states/stateCalcUtils.ts`.

Deductions for every jurisdiction live in `lib/deductionCalculator.ts`. Capital gains, losses and carryovers are netted once, in `netCapitalGains()` in `lib/taxUtils.ts`, for both federal and state.

Payroll tax on wages (Social Security and Medicare) is calculated and shown for information only. It is not part of the tax total, the amount owed, or the safe harbor test, because employers withhold it.

### MCP Interface

`POST /api/mcp` is a public, read-only MCP Streamable HTTP endpoint built on the official MCP TypeScript SDK (`@modelcontextprotocol/server` v2) in stateless mode, the same shape as dawnward's. A fresh `McpServer` is built per request by `createTaxServer()` in `lib/mcp/server.ts`; GET and DELETE session operations return 405.

**Tools:** `estimate_tax`, `check_safe_harbor`, `compare_charitable_giving`, `compare_filing_status`, `estimate_withholding`, `list_jurisdictions`. Each takes the whole return in the call (`TaxInputs` field names, camelCase) and returns JSON as text and `structuredContent`, rounded to cents. `estimate_tax` also returns `notes` (the sentences the page shows where a rule limited a figure), `assumptions` (what was filled in for a field the caller left out, with a `source`) and `data` (the year's verification status from `lib/mcp/dataStatus.ts`, which must track `data/VERIFICATION.md`).

**Rate limited:** 600 requests per hour per IP (`lib/rateLimiter.ts`, `lib/clientIp.ts`, copied from dawnward). No authentication: the tools are pure calculations and the server holds no state.

**Schemas:** the Zod objects in `lib/mcp/schemas.ts` are the single source of truth. The SDK validates arguments against them and derives the `tools/list` JSON Schema from them, so the `.describe()` text is what an assistant reads. Unlike on-screen text, these descriptions may name forms and boxes, because the reader is a model mapping documents onto fields. Validation failures come back as tool results with `isError: true`.

**Testing:** `app/api/mcp/__tests__/route.test.ts` drives the route with real protocol requests. `bun run mcp:exercise` goes further: it connects to a running server on port 3457 (`bun run dev -- -p 3457`) with the official MCP client and calls every tool for every state, year and filing status, comparing the results with `lib/calculate.ts`. Run it before pushing a change to the route, the schemas or the tools.

**Privacy:** the route logs only the HTTP method and status, and the tool name and duration. Never log request bodies, tool arguments or results, and never add storage to the route. The README's Privacy section describes the endpoint; keep it accurate.

### Multi-Year Data

All tax data JSON files are keyed by year (e.g., `"2025": { ... }`). Supported years and the default year are set in `lib/config.ts`; the user picks the year in the UI. Rules that start or change in a given year belong in the data (for example a rate of 0 for earlier years), not in year checks in the code.

Federal law changes do not automatically apply to states. Before reusing a federal rule in a state calculation, check whether that state conforms.

## Common Tasks

### Adding a New State

Follow the guide in `README.md` under "Adding a New State". The pattern is well-established.

### Adding a New Input Field

Keep inputs to the minimum the calculation needs; prefer deriving a value from existing inputs over asking for a new one.

The forms are progressive: a field that only matters once another has a value is a sub-field. It appears when its parent has a value and never hides while it holds a value of its own, so nothing on screen is affected by a number the user cannot see. Add new detail fields this way rather than as always-visible inputs.

1. Add field to `TaxInputs` type in `lib/types.ts`
2. Add to `defaultInputs` in `TaxCalculator.tsx`, and to `buildSpouseInputs()` in `lib/spouseInputs.ts` so the married-filing-separately comparison splits it
3. Add to `createDefaultInputs()` in `lib/__tests__/testData.ts` and to the fixture in the filing status comparison modal test
4. Add UI in appropriate form component (`Forms/`)
5. Update calculators to use the new field
6. Add tests

Write the label and hint following "Writing On-Screen Text" below.

### Writing On-Screen Text

This covers everything a person reads in the app: labels, hints, warnings, notes, dialog text and the result breakdowns.

- Describe what to enter, or what happened, in plain terms: "Wages and salary", not "W-2 wages".
- Do not refer to tax forms, schedules, line or box numbers (W-2, 1099, Schedule A). People use this to estimate before those forms exist.
- Common tax abbreviations are fine where space is tight (AGI, SALT, MFJ, MFS, LTCG): the audience knows them.
- Form names, statute references and sources belong in code comments and `data/VERIFICATION.md`, not on screen.
- When a rule limits or changes a number, say so in a short note next to it, in the same plain terms.

### Modifying Tax Calculations

1. Update the relevant calculator in `lib/` or `lib/states/`
2. Update or add tests in `lib/__tests__/`, with the arithmetic shown in a comment
3. Run `bun run test:run` to verify

When a test's expected value changes, work out the new value from the rule by hand; do not copy it from the failing output.

### Updating Tax Data

When updating tax brackets, deductions, limits, or the rules that use them:

1. Always verify values against official government sources (IRS, FTB, DOR, etc.), using the statute or the form instructions where possible
2. Update `data/VERIFICATION.md` with the source URL and verification date, and record corrections and known approximations there
3. If an official value is not published yet, reuse the prior year's value, mark it as WAITING in `data/VERIFICATION.md`, and add it to the pending items list
4. Update affected tests with correct expected values
5. Run `bun run test:run` and `bun run build` to verify all tests pass

## Design Documents

Significant features get a design document before any code: the problem, the options with evidence, the decisions still open and who makes them, then the implementation plan once those are settled. All of them live in `design_docs/`, which is listed in `.gitignore` and stays on the owner's machine; do not create a separate `docs/` directory.

```
design_docs/
  completed/      # Implemented features (archived, do not edit)
  exploration/    # Ideas and scopes still being decided
  shovel_ready/   # Scoped, decisions made, ready to implement
```

A design starts in `exploration/`, moves to `shovel_ready/` when its open decisions are closed and it has a plan, and to `completed/` once implemented. Research and sources go in the document; the repository is public, so nothing private from other projects or people belongs in it.

## Before Committing

Always run linters and tests before committing changes:

```bash
bun run lint       # ESLint
bun run test:run   # Vitest
bun run build      # Production build
```

All tests must pass and the build must succeed. For changes to what is shown on screen, also check the result in a browser.

Commit directly to `main`, in focused commits that each do one thing. Commit and push only when asked.

For significant code changes, use the code-simplifier skill to refine code for clarity.

Tests are colocated with their components:

- `lib/__tests__/` for calculation logic
- `components/*/__tests__/` for React components

## Code Style

- No emojis in code or comments
- Use existing patterns - check similar files before creating new ones
- Prefer editing existing files over creating new ones
- Keep components focused and single-purpose
- Use TypeScript strictly - avoid `any` types
- Alphabetize whenever possible
- Prettier is not a project dependency and older files are not uniformly formatted. Match the surrounding formatting and do not reformat code you are not otherwise changing.

## Performance

Use the `vercel-react-best-practices` skill when writing or refactoring React components, adding data fetching, or working on components that render frequently.

This codebase already implements several React best practices:

- **Dynamic imports**: State breakdown components use `next/dynamic` for code-splitting
- **Lazy data loading**: State tax data loads on-demand via `lib/stateData.ts`
- **React.memo**: Display components are memoized to prevent unnecessary re-renders
- **useMemo/useCallback**: Expensive calculations and callbacks are memoized in `TaxCalculator.tsx`
- **Stable keys**: List items use stable identifiers, not array indices
